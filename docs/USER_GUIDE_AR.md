## 1. فكرة البرنامج في دقيقة

```
أنت (المدير) ── تكتب طلبًا واحدًا
      │
      ▼
وكيل التخطيط (المدير — نموذج Claude تختاره أنت)
      │  يحلّل الطلب، يقسّمه إلى مهام، يحدد معايير القبول
      ▼
طابور المهام ──► 4 عمّال متخصصين يعملون بالتوازي
                  ١ بحث وتحليل · ٢ هندسة وتطوير · ٣ جودة وأمان · ٤ توثيق واستراتيجية
                  كل عامل إما «تلقائي» (نموذج أو جلسة Arena) أو «بمساعدة شخص» (موظف)
      │
      ▼
المراجعة ── المدير يقترح، وقواعد المنصة الثابتة تقرّر، وأنت تقرّر في الأمور الحرجة
      │
      ▼
الدمج / الإكمال ── لا يُدمج كود ولا تكتمل مهمة حرجة إلا بموافقة شخص
      │
      ▼
تقرير واحد يبيّن لكل نتيجة: هل تحققت منها المنصة؟ هل وافق عليها شخص؟ أم هي مجرد ادعاء؟
```

قواعد ثابتة لا يستطيع أي وكيل تجاوزها (مفروضة في الخادم وليس في الواجهة فقط):

- لا دمج في الفرع الرئيسي دون موافقة شخص في **مركز الموافقات**.
- لا يُرسَل أي شيء إلى Arena قبل أن تُقرّ بشروطه بنفسك.
- الفريق الافتراضي لا يرسل شيئًا لأي جهة: المدير بلا نموذج، والعمّال الأربعة «بمساعدة شخص».

## 2. التثبيت والتشغيل على أوبنتو

**المتطلبات:** Docker مع Docker Compose، وgit.

### التثبيت أول مرة

```bash
git clone https://github.com/oldman-552/ai-agent-command-center.git
cd ai-agent-command-center
./install.sh        # يجهّز ملف .env ويطلب منك كلمة مرور المدير العام (12 حرفًا على الأقل)
./start.sh          # يبني ويشغّل كل شيء — أول مرة قد تأخذ 5 إلى 15 دقيقة
```

ثم افتح **http://localhost:3000**.

### الأوامر اليومية

| الأمر | ماذا يفعل |
|---|---|
| `./start.sh` | تشغيل المنصة |
| `./stop.sh` | إيقافها (البيانات تبقى) |
| `./update.sh` | جلب آخر نسخة من GitHub وإعادة البناء والتشغيل |
| `./health-check.sh` | فحص صحة كل الخدمات |

لا تستخدم `docker compose down -v` إلا إذا أردت **حذف كل البيانات**.

### المنافذ

| المنفذ | الاستخدام | الإعداد في `.env` |
|---|---|---|
| 3000 | الموقع (هذا ما تفتحه في المتصفح) | `FRONTEND_PORT` |
| 8000 | الواجهة البرمجية (API) | `API_PORT` |
| 15672 | لوحة RabbitMQ | `RABBITMQ_UI_PORT` |

كل المنافذ مربوطة بـ `127.0.0.1` فقط، أي أنها لا تُفتح للشبكة. إذا كان منفذ مشغولًا ببرنامج آخر (مثلًا مشروع OSINT
يستخدم 8000)، غيّره في `.env` ثم شغّل `./start.sh`:

```bash
sed -i 's/^API_PORT=.*/API_PORT=8010/' .env
```

## 3. أول دخول

- **اسم المستخدم:** `admin` (القيمة `ADMIN_USERNAME` في `.env`).
- **كلمة المرور:** التي اخترتها أثناء `./install.sh`. إذا نسيتها:

```bash
grep '^ADMIN_PASSWORD' .env
```

هذا الحساب هو **المدير العام (Super Admin)**، وهو الوحيد الذي يستطيع ربط Arena Local Bridge والإقرار بشروط Arena.
غيّر اللغة والمظهر من أعلى الصفحة.

## 5. إعداد فريق العمل الذكي خطوة بخطوة

### 5.1 إنشاء الفريق

افتح **فريق العمل الذكي**. إذا ظهرت رسالة «لا يوجد فريق عمل ذكي لهذه المنظمة بعد»، اضغط **إنشاء الفريق الافتراضي**.
ستحصل على مدير بلا نموذج وأربعة عمّال في وضع «بمساعدة شخص».

### 5.2 مزوّد للمدير

المدير يحتاج نموذج محادثة حقيقيًا يقبل تعليمات ويُرجع إجابات منظّمة. **جلسة Arena لا تصلح مديرًا.**

- **للعمل الحقيقي:** افتح **المزوّدون والنماذج** ← **إضافة مزوّد** ← «Anthropic (Claude API)»، والصق مفتاح API
  من لوحة مطوّري Anthropic، ثم **اختبار الاتصال** و**اكتشاف النماذج**. اشتراك Claude.ai العادي لا يشمل مفتاح API.
- **للتجربة فقط:** يوجد مزوّد جاهز اسمه «Mock Provider (TEST ONLY — not real AI)». خططه ومراجعاته نصوص اختبار
  ثابتة، وكل ما يمر عبره يُوسَم **تجريبي** في كل مكان.

### 5.3 ضبط المدير

**فريق العمل الذكي ← المدير والعمّال ← المدير ← ضبط:**

| الحقل | ماذا تختار |
|---|---|
| النموذج | نموذج Claude (أو mock-model للتجربة) |
| النموذج الاحتياطي | اختياري: يُستخدم إذا تعطّل الأول |
| المراجعة | «المدير يراجع النتائج» أو «شخص يراجع كل نتيجة» |
| عدد التعديلات قبل أن يقرّر شخص | بعده تذهب النتيجة إليك بدل إعادتها مرة أخرى |
| تعليمات إضافية | أسلوبك وقواعدك. لا تستطيع إيقاف قواعد المراجعة في المنصة |

دون نموذج للمدير يُرفض أي هدف جديد بالرسالة «المدير لا يستطيع العمل بعد».

### 5.4 العمّال الأربعة

لكل عامل زر **ضبط**، وفيه:

- **طريقة عمل هذا العامل:**
  - **تلقائي:** المنصة ترسل المهمة إلى مزوّد العامل (نموذج API أو جلسة Arena عبر الجسر) وتستلم الجواب.
  - **بمساعدة شخص:** موظف يأخذ بطاقة المهمة، ينفّذها (في Arena أو بنفسه)، ويلصق النتيجة. لا يحتاج جسرًا.
  - **معطَّل:** لا يستلم مهام، والمدير يعطيها لعامل آخر يملك المهارات نفسها.
- **المهارات:** المدير يعطي المهمة فقط لعامل يملك كل المهارات المطلوبة.
- **المزوّد / النموذج / الجلسة:** للعامل التلقائي. **اختر جلسة مختلفة لكل عامل**، وإلا اختلطت رسائلهم في
  محادثة Arena واحدة (تظهر لك تحذيرًا بذلك).
- **الشخص:** لوضع «بمساعدة شخص». اختر موظفًا بعينه أو «أي شخص مسموح له بالعمل».
- **سلّم المهمة إلى شخص عندما يتعذّر العمل التلقائي:** مستحسن. إذا تعطّل الجسر أو خرج الحساب، تتحول المهمة
  إلى بطاقة لشخص بدل أن تفشل.
- **المهلة وعدد المحاولات وتعليمات العامل.**

التغييرات تُطبَّق على المهام الجديدة فقط، والمهمة الجارية لا تُقاطَع.

### 5.5 حسابات لموظفيك (مهم)

**الإعدادات ← المستخدمون ← إضافة مستخدم** لكل موظف (كلمة مرور 12 حرفًا على الأقل)، وأعطه دورًا يسمح له بالعمل
على المهام.

لماذا هذا مهم؟ **من سلّم نتيجة حرجة أو كودًا لا يستطيع الموافقة عليها بنفسه.** إذا عملت وحدك ونفّذت المهمة
بيدك، تحتاج شخصًا ثانيًا يوافق في مركز الموافقات.

## 6. إعطاء الفريق هدفًا

من **غرفة العمليات ← هدف جديد**، أو من **نظرة عامة ← أعطِ الفريق هدفًا**:

1. **ما المطلوب؟** اكتب الهدف كما تكتبه لموظف.
2. **عنوان قصير** (اختياري).
3. **من يراجع النتائج؟** المدير أو شخص.
4. **إرسال إلى المدير.**

المدير يحلّل ويخطّط (حتى 12 مهمة، لكل منها معيار قبول واحد على الأقل)، ثم يوزّع. تتابع ذلك حيًّا في غرفة العمليات.

### كيف تكتب طلبًا جيدًا

- **النتيجة المطلوبة:** «صفحة دفع تقبل البطاقات وApple Pay».
- **القيود:** «بالعربي والإنجليزي، على قاعدة PostgreSQL الحالية».
- **متى يكتمل العمل:** «عندما تنجح الاختبارات وتُراجع الصفحة».
- **لا تلصق كلمات مرور أو مفاتيح.** أي شيء يشبه سرًّا يُحذف تلقائيًا قبل الحفظ والإرسال.

## 7. العمل «بمساعدة شخص» — دور موظفيك

عندما تذهب مهمة إلى عامل في وضع «بمساعدة شخص»، تظهر بطاقة بحالة **بانتظار شخص** في:
غرفة العمليات (فقاعة «مهمة تنتظر من يأخذها» وزر **خذها**)، و**يحتاجك الآن**، وقسم **المهام**.

خطوات الموظف:

1. يفتح البطاقة ويضغط **قبول هذه المهمة**. بعدها هو فقط يستطيع تسليم نتيجتها.
2. ينسخ **الرسالة الجاهزة** (هي نفسها التي كانت ستُرسل لنموذج) ويلصقها في Arena أو ينفّذ العمل بنفسه.
3. يلصق الجواب في **النتيجة** كما استلمه تمامًا، ويضيف **ملاحظات** و**ملفات** إن لزم.
4. **تسليم النتيجة.** تُحفظ كنسخة جديدة غير قابلة للتعديل، ثم تُراجَع.

إذا لم يستطع، يضغط **إعادة** ويكتب السبب، فتعود المهمة لتُسند من جديد.

> إذا تحوّلت مهمة تلقائية إلى شخص بعد فشل، قد تظهر ملاحظة «ربما وصل الطلب إلى جلسة Arena». انظر في الجلسة
> أولًا، فقد يكون الجواب هناك، فلا ترسل الطلب مرتين.

## 8. المراجعة والقرارات والموافقات

### من يقرّر؟

- **المدير يقترح** حكمًا لكل معيار قبول مع اقتباس من النتيجة.
- **قواعد المنصة تقرّر** ولا يغيّرها أي نموذج:
  - معيار غير متحقق ← لا قبول أبدًا.
  - نتيجة فارغة ← لا قبول.
  - بعد الحد الأقصى للتعديلات ← القرار لشخص.
  - نتيجة فيها نص يشبه تعليمات موجّهة للنموذج ← القرار لشخص.
  - نتيجة فيها شيء يشبه كلمة سر أو مفتاح ← لا تُرسل لأي نموذج.
- **أنت تستطيع التدخل في أي وقت.**

### قرارك على نتيجة

في بطاقة المهمة، قسم **القرار في النسخة …**: **موافقة** · **طلب تعديل** · **رفض**. طلب التعديل والرفض يحتاجان
ملاحظة. ومن البطاقة نفسها: **إعادة إسناد** لعامل آخر، **إعادة فتح**، **إلغاء المهمة**، أو **اطلب من المدير المراجعة
مرة أخرى**.

### المهام الحرجة ومركز الموافقات

مهمة فيها عملية حرجة (نشر، إصدار عام، دمج كود…) لا تكتمل بمجرد نجاح المراجعة. تصبح حالتها
**روجعت — بانتظار الموافقة**، ويظهر طلب في **مركز الموافقات** يحمل رقم النسخة وبصمتها:

- الموافقة تُكمل المهمة. تغيّر النتيجة بعدها يحتاج موافقة جديدة.
- **من قدّم النتيجة لا يستطيع الموافقة عليها.** يلزم شخص آخر له صلاحية الموافقة.

## 9. مهام التطوير (كود)

العمّال يكتبون نصًا فقط، والمنصة هي التي تحوّل النص إلى كود مختبَر.

### التفعيل

**المدير والعمّال ← مهام التطوير (كود):**

1. علّم **تفعيل مهام التطوير**.
2. **أمر الاختبارات:** مثلًا `python3 -m pytest -q`. تُقبل فقط الأوامر المسموحة في الصندوق المعزول.
   إذا تركته فارغًا يُطبَّق الكود دون فحص، ولن يُصنَّف «تحققت منه المنصة» أبدًا.
3. **مهلة الاختبارات** ثم **احفظ**.

يجب أن يكون الهدف مربوطًا بمشروع له مستودع.

### كيف تسير مهمة كود

1. المدير يخطط مهمة **مهمة كود** ويحدد الملفات التي يحتاج العامل أن يراها.
2. رسالة العامل تشرح صيغة التسليم وتعرض قائمة ملفات المستودع.
3. العامل يسلّم كل ملف أنشأه أو غيّره **كاملًا** في كتلة تبدأ بـ ```` ```file:المسار ````، أو ```` ```delete:المسار ````
   للحذف.
4. المنصة تطبّق هذه النسخة على فرع المهمة `agent/<worker>/task-<id>` فوق الفرع الرئيسي كما هو الآن، وتعمل commit،
   ثم تشغّل الاختبارات في الصندوق المعزول (بلا إنترنت، بموارد محدودة).
5. لا كتل، مسار غير آمن، لا تغيير، أو اختبارات فاشلة ← تعود النتيجة للعامل مع مخرجات المنصة نفسها، **دون سؤال أي
   نموذج**.
6. نجحت الاختبارات ← يراجعها المدير كالمعتاد. القبول **لا يدمج**: يُنشئ طلب دمج في **مركز الموافقات** لنفس
   الـ commit المختبَر بالضبط.
7. بعد موافقة شخص (غير من سلّم النتيجة) تدمج المنصة. إذا تغيّر الفرع الرئيسي وتعذّر الدمج، تعود المهمة مع السبب.

ترى كل هذا في بطاقة المهمة تحت **فحص المنصة للكود** (الفرع، الملفات، الاختبارات)، وفي شاشة العامل في غرفة
العمليات.

> الدمج يتم في نسخة المشروع داخل المنصة. فتح طلب دمج على GitHub لمهام فريق العمل الذكي غير مبني بعد.

## 10. التقرير النهائي وأصنافه

عندما تنتهي كل المهام (أو تفشل أو تُلغى) يُكتب تقرير يمكنك **تنزيله (Markdown)**. كل نتيجة في صنف واحد فقط،
تحسبه المنصة من سجلاتها هي، لا مما كتبه نموذج:

| الصنف | المعنى |
|---|---|
| **تحققت منها المنصّة** | مهمة كود نجحت اختباراتها على النسخة المقبولة نفسها. أقوى صنف |
| **وافق عليها شخص** | قبلها إنسان، في المراجعة أو في مركز الموافقات |
| **مقترحات العمّال** | قبلها المدير، وكل اقتباس قدّمه موجود فعلًا في النص |
| **ادعاءات غير متحقَّق منها** | قبلها المدير بحكمه وحده |
| **فشلت أو رُفضت** | — |
| **غير مكتملة** | — |

**ما سجّلته المنصّة:** جمل محسوبة من سجلات المنصة. **ملخص المدير** نص من نموذج للقراءة فقط، ولا يغيّر الأصناف.
أي شيء مرّ بمزوّد تجريبي أو بالجسر المزيّف موسوم **تجريبي**. الهدف لا يُعتبر مكتملًا إلا إذا اكتملت كل مهامه.

## 11. غرفة العمليات

**فريق العمل الذكي ← غرفة العمليات.** ثلاث طرق عرض في الأعلى:

### الخريطة الحيّة

- المسار كاملًا: **أنت — المدير ← وكيل التخطيط ← طابور المهام ← العمّال ← المراجعة ← مكتملة**.
- لكل عامل لون وحلقة تبيّن مرحلته (أُسندت ← يعمل ← سلّم ← روجعت ← اكتملت).
- الخطوط المضيئة والنقاط المتحركة مهام تتحرك فعلًا. المؤثرات لا تظهر إلا عند تغيّر حقيقي بين قراءتين.
- الفقاعات على الخريطة: **خذها** لمهمة تنتظر شخصًا، و**اقبل** أو **وافق وادمج** لقرار مطلوب منك.
- **اضغط أي عامل** لتفتح **شاشة العامل**: خطوات المهمة، وما يكتبه العامل التلقائي لحظة بلحظة، والنتيجة التي ألصقها
  الشخص، و**فحص المنصة للكود**. ومنها **افتح بطاقة المهمة** أو **إعدادات العامل**.
- **شريط اليوم:** مسار لكل عامل من سجل المهام. ◆ عُرضت على شخص · ● اكتملت · ↺ طُلب تعديل · ▲ تعثّر.
- على الجانب: **يحتاجك الآن** · **نجم اليوم** · **ما يحدث الآن** · **العمّال**.

### ملخص اليوم

نجم اليوم، جوائز اليوم (الأسرع، الأدق، أمور تنتظرك)، المهام المكتملة هذا الأسبوع، إنجاز كل عامل، أرقام الآن،
ومفاتيح **التنبيهات والمؤثرات**.

### شاشة كبيرة

أرقام ضخمة وبطاقة لكل عامل وتقدّم الهدف، لتعرضها على تلفاز في المكتب. زر **ملء الشاشة** في الأعلى.

### أزرار الأعلى

**طاقة الفريق** (كم عاملًا يعمل الآن) · **يحتاجك** (عدد ما ينتظر قرارك) · **إيقاف المؤثرات مؤقتًا** ·
الصوت (مغلق حتى تشغّله) · **جرّب المؤثرات** (عرض فقط، لا يغيّر شيئًا في العمل) · **هدف جديد**.

## 12. ربط Arena Local Bridge على أوبنتو

> **اقرأ قبل الاستخدام:** Arena Local Bridge ليس واجهة رسمية من Arena. هو يتحكم بموقع Arena عبر حساباتك المسجّلة،
> وشروط Arena تمنع الاستخدام الآلي، فقد تُوقَف حساباتك. **لست مضطرًا للجسر:** وضع «بمساعدة شخص» يعمل دونه.
>
> الخطوات التالية مكتوبة من قراءة كود الجسر، ولم تُجرَّب على جهاز أوبنتو حقيقي.

**لماذا خطوة إضافية على أوبنتو؟** الجسر يستمع على `127.0.0.1` فقط. على لينكس لا تصل حاويات Docker إلى هذا العنوان
(بعكس Docker Desktop على ويندوز)، فنحتاج وسيطًا صغيرًا (`socat`) يمرّر الاتصال من شبكة Docker إلى الجسر.

### 1) Node.js 20 أو أحدث

```bash
node -v
# إذا كان أقل من 20 أو غير موجود:
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
```

### 2) تنزيل الجسر وإنشاء مفتاحه

```bash
git clone https://github.com/Gandhara2077/arena-local-bridge.git ~/arena-local-bridge
cd ~/arena-local-bridge
npm install
mkdir -p ~/.arena-bridge
KEY=$(openssl rand -hex 24)
echo "ARENA_AGENT_BRIDGE_KEY=$KEY" >> ~/.arena-bridge/.env
echo "مفتاح الجسر: $KEY"      # احفظه
```

### 3) تشغيل الجسر وتسجيل الحسابات

```bash
cd ~/arena-local-bridge && npm start      # اترك النافذة مفتوحة
```

واجهة الجسر صينية فقط. لتحويلها إلى العربية أو الإنجليزية، شغّل هذا مرة واحدة من مجلد المنصة (يضيف زر اللغة
**العربية / English / 中文** أسفل يمين الصفحة، ولا يغيّر عمل الجسر):

```bash
cd ~/ai-agent-command-center && tools/arena-bridge-i18n/apply.sh ~/arena-local-bridge
```

للتراجع: أضف `--undo`. وقبل `git pull` في مجلد الجسر نفّذ `--undo` ثم أعد التطبيق بعده.

افتح **http://127.0.0.1:20140** في Chrome، وسجّل الدخول بكل حساب Arena، وتأكد أن لكل حساب **جلسة (محادثة) واحدة
على الأقل**. كل عامل سيستخدم جلسة.

### 4) فتح الطريق من Docker إلى الجسر (نافذة جديدة)

```bash
sudo apt install -y socat
GW=$(ip -4 addr show docker0 | grep -oP 'inet \K[\d.]+'); echo $GW     # غالبًا 172.17.0.1
socat TCP-LISTEN:20140,bind=$GW,reuseaddr,fork TCP:127.0.0.1:20140     # اترك النافذة مفتوحة
```

إذا كان الجدار الناري مفعّلًا (`sudo ufw status` يقول active):

```bash
sudo ufw allow from 172.16.0.0/12 to 172.17.0.1 port 20140 proto tcp
```

> هذا الوسيط يجعل الجسر متاحًا لكل حاويات جهازك (ومنها مشاريعك الأخرى). على جهاز شخصي الخطر صغير، لكن أغلق نافذة
> `socat` عندما لا تستخدم العمّال التلقائيين.

### 5) في المنصة

**فريق العمل الذكي ← Arena Local Bridge ← إضافة جسر:**

| الحقل | القيمة |
|---|---|
| الاسم | مثلًا «جسر المكتب» |
| العنوان | `http://host.docker.internal:20140` |
| مفتاح الجسر | المفتاح من الخطوة 2 (ليس كلمة مرور Arena) |
| ترويسة Host | اتركها كما هي (`127.0.0.1:20140`) |
| البث المتدفق | مفعّل (مستحسن) |

ثم:

1. **اختبار الاتصال:** يجب أن تنجح كل الخطوات. لا يُرسل أي شيء إلى Arena أثناء الاختبار.
2. **البحث عن الجلسات:** تظهر جلسات حساباتك (العناوين مقنّعة).
3. **الإقرار بالشروط:** اقرأ شروط Arena، وعلّم «قرأتُ الشروط وأقبل هذا النص». يُسجَّل باسمك، ويمكنك **سحب الإقرار**
   متى شئت. تغيير عنوان الجسر يسحب الإقرار تلقائيًا.
4. **المدير والعمّال:** اجعل العامل **تلقائي**، واختر المزوّد (الجسر) و**الجلسة**. جلسة مختلفة لكل عامل.

### حدود الجسر (لا تستطيع المنصة إصلاحها)

- لا يذكر الجسر أي حساب أجاب، فربط العامل بالحساب «إعداد» وليس إثباتًا.
- ينفّذ طلبًا واحدًا في كل مرة، فأربعة عمّال على جسر واحد لا يعملون فعلًا بالتوازي.
- لا يذكر الاستهلاك، فيظهر «المزوّد لم يذكر الاستهلاك».
- الطلب الذي تتخلى عنه المنصة قد يستمر داخل الجسر، فلا يُعاد إرساله أعمى.

## 13. مثال كامل: أنت وأربعة موظفين

**الإعداد مرة واحدة:**

1. أضف مفتاح Claude في **المزوّدون والنماذج**، واختره نموذجًا للمدير.
2. أضف أربعة مستخدمين لموظفيك في **الإعدادات ← المستخدمون**.
3. في **المدير والعمّال** اجعل كل عامل «بمساعدة شخص» واختر له موظفًا:
   العامل ١ (بحث) ← موظف أ · العامل ٢ (تطوير) ← موظف ب · العامل ٣ (جودة) ← موظف ج · العامل ٤ (توثيق) ← موظف د.
4. (اختياري) فعّل **مهام التطوير** بأمر الاختبارات.

**كل يوم:**

1. أنت: **هدف جديد** ← «أريد صفحة دفع لمتجرنا تقبل البطاقات، مع اختبارات، بالعربي والإنجليزي».
2. المدير يقسّمه، مثلًا: تحليل المتطلبات (١)، الواجهة البرمجية (٢، كود)، الاختبارات والمراجعة الأمنية (٣)،
   دليل الاستخدام (٤).
3. كل موظف يدخل بحسابه، ويرى بطاقته، ويضغط **قبول**، ويلصق الرسالة في Arena، ثم يلصق الجواب و**يسلّم النتيجة**.
4. المدير يراجع. ما لا يحقق المعايير يعود للموظف بـ **طلب تعديل** مع السبب.
5. مهمة الكود: المنصة تطبّقها وتختبرها، ثم يظهر لك **وافق وادمج** في **يحتاجك الآن** أو في **مركز الموافقات**.
   (الموظف الذي سلّم الكود لا يستطيع الموافقة، وأنت تستطيع.)
6. تتابع كل هذا على **غرفة العمليات**، أو تعرضها على الشاشة الكبيرة في المكتب.
7. في النهاية: **التقرير** يبيّن ما تحققت منه المنصة، وما وافقت عليه، وما هو مجرد اقتراح.

لاحقًا، إذا ربطت Arena Local Bridge، تستطيع جعل أي عامل «تلقائي» مع إبقاء خيار **سلّم المهمة إلى شخص** مفعّلًا، فإذا
تعطّل الجسر تذهب المهمة لموظفك تلقائيًا.

## 14. حل المشاكل الشائعة

| ما تراه | السبب | الحل |
|---|---|---|
| `Bind for 0.0.0.0:8000 failed: port is already allocated` | برنامج آخر يستخدم المنفذ | غيّر `API_PORT` (أو `FRONTEND_PORT`) في `.env` ثم `./start.sh` |
| `containerd.sock: timeout` وكل الحاويات unhealthy | Docker نفسه علق | `sudo systemctl restart containerd && sudo systemctl restart docker` ثم `./stop.sh && ./start.sh` |
| `password authentication failed for user "acc"` | ملف `.env` ناقص | `git pull` ثم `./install.sh` (يكمل القيم الناقصة) ثم `./start.sh` |
| الموقع لا يفتح بعد `./start.sh` مباشرة | البناء لم ينتهِ | انتظر رسالة النجاح. تابع: `ls -t logs \| head -1` ثم `tail` على الملف |
| «تعذّر الاتصال بالخادم» | الواجهة البرمجية متوقفة | `./health-check.sh` و`docker compose ps -a` |
| «المدير لا يستطيع العمل بعد» | لم يُختر نموذج للمدير | المدير والعمّال ← المدير ← ضبط |
| الموافقة مرفوضة في مركز الموافقات | أنت من سلّم النتيجة | يوافق شخص آخر له صلاحية الموافقة |
| اختبار الجسر يفشل في خطوة «العنوان» | الحاويات لا تصل للجسر | تأكد أن `socat` يعمل وأن الجدار الناري يسمح (القسم 12) |
| الجسر يرد 403 | ترويسة Host غير محلية | اتركها `127.0.0.1:20140` |
| مهام عامل تلقائي تذهب لشخص | الجسر متوقف، الشروط غير مُقرّ بها، أو الحساب خرج | انظر صفحة Arena Local Bridge ← **تحديث الحالة** |
| «الصندوق المعزول غير متاح» في مهمة كود | Docker sandbox غير متاح للعامل | الكود يُطبَّق دون اختبارات ولن يُصنّف «تحققت منه المنصة» |

إن لم تجد حلك هنا: [TROUBLESHOOTING.md](TROUBLESHOOTING.md).

## 15. حدود يجب أن تعرفها

- **لم يُجرَّب مع حسابات حقيقية:** المدير على نموذج Claude حقيقي، وعمّال Arena عبر جسر حقيقي بأربعة حسابات.
  الملف `REAL-TESTS.bat` (لويندوز) والاختباران `backend/tests/test_real_provider.py` و`test_real_arena.py` مخصّصة لذلك.
- **العمّال عبر Arena نصّيون:** لا يشغّلون أدوات ولا اختبارات. المنصة هي التي تطبّق كودهم وتختبره (القسم 9).
- **الدمج محلي:** مهام الكود تُدمج في نسخة المشروع داخل المنصة، ولا يُفتح لها طلب دمج على GitHub بعد.
- **المراجعة بجودة نموذج المدير:** القواعد تمنع الحالات السيئة المعروفة، لكنها لا تجعل الجواب الخاطئ صحيحًا.
- **شروط Arena:** الجسر غير رسمي، والمخاطرة على الحسابات قائمة مهما كانت حماية المنصة.
